# キラーコンテンツ分析 — TikTok / BeReal とその先

## この文書の目的

「TikTok やBeReal のようなキラーコンテンツをモバイルアプリで作りたい」という問いに答えるための分析メモ。
事例を並べるだけでは再現できないので、**分解のフレームワーク**を先に定義し、それで既存の勝ち筋を採点し、
最後に本リポジトリ（latent）に当てはめる。

出典は末尾にまとめた。数値は出典に書かれている範囲のみ記載し、推測値は書いていない。

---

## 1. 前提のずらし — 「コンテンツ」ではなく「制約」が勝っている

最初に、言葉の定義を正しておく必要がある。

TikTok のキラーコンテンツは「動画」ではない。BeReal のキラーコンテンツは「加工なしの写真」ではない。
どちらの場合も、勝っているのは**ユーザーの行動を一意に決める制約**のほうだ。

| アプリ | 表面上のコンテンツ | 実際に効いている制約 |
|---|---|---|
| TikTok | 短尺動画 | フォロー関係を無視して興味だけで配信する（インタレストグラフ） |
| BeReal | 無加工の日常写真 | ランダム通知から2分以内・前後カメラ同時 |
| Setlog | 日常のVlog | 毎時アラーム・2〜4秒・撮り直し不可・カメラロールからの投稿不可 |
| Locket | 友達の写真 | ホーム画面ウィジェットに直接届く・友達数の上限あり |
| Spotify Wrapped | 個人の再生統計 | 年に1回・全員同時 |

つまり作るべきものは「面白いコンテンツ」ではなく、**「面白いコンテンツが自動的に生えてくる制約」**である。
以降、この制約のことを本文書では「メカニクス」と呼ぶ。

---

## 2. 分解フレームワーク（6軸）

キラーメカニクスを評価するための6つの軸。新しいアイデアを思いついたら、この6軸で採点する。

### 軸1: 強制関数（Forcing Function）— いま行動する理由があるか

「好きなときに使ってください」で使われるアプリはない。**いま**やる理由を設計で作る。

- BeReal: ランダム通知 → 2分以内。時間が理由になる。
- Setlog: 毎時のアラーム。1日に十数回の強制点がある。
- Spotify Wrapped: 年1回、全員同時に配信。タイムラインが一斉に埋まる。
- Duolingo: ストリーク。「途切れる」という損失が理由になる。

強制関数がないアプリは、どれだけ体験が良くても「思い出したときだけ開くアプリ」になる。

### 軸2: 投稿コストをゼロにする制約 — 白紙の恐怖を消せているか

ここが最も誤解されやすい。**制約はユーザーを縛るためではなく、免罪符を与えるために置く。**

Setlog が「2〜4秒・撮り直し不可・編集不可」なのは、機能をケチっているのではない。
撮り直せないなら、下手に撮れても自分のせいではない。だから投稿できる。
「うまくやらなくていい」という許可を、制約の形で配っている。

逆に、編集機能・フィルタ・下書きを足すほど、投稿は「作品」になり、投稿率は落ちる。
BeReal が失速した理由のひとつはここで、**制約が緩んだ結果、無加工であること自体が新しい演出になった**。
「ありのまま」を目指したはずが、ありのままを演じる場になった、と複数の分析が指摘している。

### 軸3: 観測可能性 — 出力がアプリの外に漏れる形をしているか

アプリ内で完結する出力は、どれだけ良くても広まらない。出力が**外に持ち出せる形**をしている必要がある。

漏れ方には3種類ある。

1. **スクリーンショット型**: Spotify Wrapped。縦長・1枚・文字が大きい。ストーリーズに貼るために設計されている。
2. **ホーム画面型**: Locket / Airbuds。ウィジェットとして常に他人の目に入る。ロック解除のたびに露出する。
3. **フィード型**: TikTok。ウォーターマーク付き動画が他プラットフォームに再投稿され、そこが入口になる。

出力が「アプリを開かないと見られない」なら、成長は広告費に依存する。

### 軸4: 社会的単位 — 誰のために作るか（これがコールドスタートを決める）

- **他人（インタレストグラフ）**: TikTok。知り合いゼロでも成立する。ただし供給側（クリエイター）を別途集める必要がある。
- **親密な少人数（インティマシーグラフ）**: BeReal / Setlog（log room は最大12人）/ Locket（友達数に上限）。
- **自分自身（アイデンティティ）**: Spotify Wrapped。他人は不要。自分を語る素材を渡す。

この選択が、そのまま次の軸を決める。

### 軸5: コールドスタート — N=1 または N=2 で成立するか

**これが個人開発における最重要の軸。**

Locket は、開発者が恋人1人のために作ったアプリで、N=2 で完全に成立していた。
だから最初のユーザーが友達を1人だけ誘えば価値が出る。結果として累計8000万DLに達している。

Setlog の log room は2〜12人。下限が「2」であることが効いている。

対して BeReal は、友達が数人いないとタイムラインが成立しない。
入口のハードルが高く、しかも一度友達が投稿をやめると連鎖的に価値が消える。

> 判定基準: **「自分ひとり、または自分と友達1人だけで使ったとき、価値があるか？」**
> ここが No のアイデアは、個人開発では立ち上がらない。

### 軸6: 反復耐性 — 200日目も面白いか（最も多くのアプリが死ぬ軸）

BeReal の通知は、200日目もまったく同じ体験である。制約は初日と同じ。だから飽きる。
DAU がピークから大幅に減少したことが複数の集計で報告されている。

これを乗り越えている3つのパターン。

| パターン | 仕組み | 例 |
|---|---|---|
| **無限供給型** | 中身が毎回違う。供給がユーザー側から無限に来る | TikTok |
| **低頻度イベント型** | そもそも頻度を上げない。年1回だから飽きない | Spotify Wrapped |
| **蓄積型** | 使うほど出力が変わる。過去の自分が素材になる | ストリーク / Setlog の日次Vlog |

Setlog は3番目に賭けている。毎時の2秒クリップは単体では無意味だが、
1日の終わりに自動で1本のVlogに合成される。**素材が意味を持つのは蓄積されたあと**、という構造になっている。
さらに、log room の全員のクリップが1本に合成されるため、他人の分も自分の出力を変える。

## 3. ケーススタディ

各事例を6軸で採点する（◎=強い / ○=あり / △=弱い / ×=なし）。

### TikTok

| 軸 | 評価 | 内容 |
|---|---|---|
| 強制関数 | ○ | 通知＋無限スクロールそのもの |
| 制約 | ○ | 短尺・縦・音源から作る |
| 観測可能性 | ◎ | ウォーターマーク付き動画が他SNSに拡散 |
| 社会的単位 | 他人 | インタレストグラフ |
| コールドスタート | ◎ | フォロワー0でも配信される。新規ユーザーの体験が初日から成立する |
| 反復耐性 | ◎ | 無限供給型 |

**本質**: 「誰をフォローしているか」ではなく「どう反応したか」で配信する設計に切り替えたこと。
投稿は一定数のユーザーに一律で配信され、そこでの視聴時間・シェア・保存が閾値を超えると次の層へ広がる。
これによりクリエイター側の参入障壁も同時に消えた（フォロワー0でも当たりうる）。

**個人開発への含意**: この構造はコンテンツ供給量が前提なので、個人では直接模倣できない。参考にすべきは
「新規ユーザーの初日体験が、既存ネットワークに依存しない」という設計思想のほう。

### BeReal

| 軸 | 評価 | 内容 |
|---|---|---|
| 強制関数 | ◎ | ランダム通知＋2分 |
| 制約 | ◎（当初） | 加工不可・前後カメラ同時 |
| 観測可能性 | △ | アプリ内で完結する。外に持ち出す形がない |
| 社会的単位 | 親密な少人数 | 友達 |
| コールドスタート | △ | 友達が複数人いないと成立しない |
| 反復耐性 | × | 通知は初日と同じ。蓄積も無限供給もない |

**失速の構造**: 軸1・軸2は満点に近い。だから爆発した。落ちたのは軸3・軸5・軸6。
特に軸6がゼロだったため、新規性が切れた瞬間に支えがなかった。
そこで機能追加に走ったが、それが軸2の制約を薄め、さらに「無加工を演じる」という本末転倒を招いた。
現在も残存ユーザーのエンゲージメント率自体は高いと報告されており、
**「深く刺さるが、飽きる」メカニクスの典型**と言える。

### Setlog（2026年時点で最も参考になる事例）

| 軸 | 評価 | 内容 |
|---|---|---|
| 強制関数 | ◎ | 毎時アラーム。1日に十数回 |
| 制約 | ◎ | 2〜4秒・撮り直し不可・カメラロール不可・後追い投稿不可 |
| 観測可能性 | ○ | 完成した日次Vlogが他SNSに投稿される。K-POPアイドルの投稿が起点になった |
| 社会的単位 | 親密な少人数 | log room 最大12人 |
| コールドスタート | ◎ | 2人から成立する |
| 反復耐性 | ○ | 蓄積型。バラバラのクリップが日の終わりに1本になる |

**数値**: ローンチから2年以内に世界累計1億DLを突破。2026年4月時点で韓国・香港のApp Store ソーシャル部門1位、
5月時点でシンガポールで1位、Androidベータも Google Play で10位。
日本でも2026年上半期の「バズったアプリ」ランキングでZ世代・アルファ世代を対象とした調査で1位（ChatGPT が2位）。

**BeReal との決定的な差**: BeReal は「1日1回の点」を作った。Setlog は「1日十数回の点を、夜に1本の線にする」。
この差がそのまま軸6（反復耐性）の差になっている。
点は飽きるが、線は「今日はどんな1本になるか」という別の興味を毎日生む。

**火のつき方**: Z世代の「作り込まれたSNSへの疲れ」という下地があったところに、
K-POPアイドル（SEVENTEEN 全メンバー、aespa の Karina など）が自分のSetlog Vlogを投稿したことが着火点になった。
これは軸3（観測可能性）が効いた事例でもある — 出力が外のSNSに出る形をしていたから、着火できた。

### Locket Widget

| 軸 | 評価 | 内容 |
|---|---|---|
| 強制関数 | ○ | ロック解除のたびに友達の写真が目に入る（受信側が強制関数） |
| 制約 | ◎ | 友達数に上限。フォロワー数という概念がない |
| 観測可能性 | ◎ | ホーム画面型。他人のスマホを覗いたときに露出する |
| 社会的単位 | 親密な少人数 | 上限つきの友達 |
| コールドスタート | ◎ | **N=2 で完全に成立**（開発者が恋人のために作った） |
| 反復耐性 | ○ | 送られてくる写真が毎回違う（相手が供給する） |

**数値**: 累計8000万DL、1250万ドルの資金調達、2022年 App Store Award（Cultural Impact）受賞。
拡散は TikTok 経由だった。

**個人開発への含意**: 本文書の中で最も再現性が高い事例。
「自分と、大切な1人」のために作ったものが、そのまま全員に効いた。
軸5が満点であることが、他のすべてを可能にしている。

### Spotify Wrapped

| 軸 | 評価 | 内容 |
|---|---|---|
| 強制関数 | ◎ | 年1回・全員同時。「乗り遅れる」圧力が働く |
| 制約 | ◎ | ユーザーは何もしない。データが勝手に溜まっている |
| 観測可能性 | ◎ | スクリーンショット型。縦長1枚・大きな数字 |
| 社会的単位 | 自分自身 | 他人不要。自己語りの素材 |
| コールドスタート | ◎ | N=1 で成立 |
| 反復耐性 | ◎ | 低頻度イベント型。1年待つから飽きようがない |

**構造**: ユーザーの投稿を一切必要としない。**すでに溜まっているデータを、語れる形に変換するだけ。**
Amazon Music、Apple Music など各社が追随し、ジャンルとして確立した。
2025年版は「listening age の比較」やリアルタイムのマルチプレイヤー機能（Wrapped Party）など、
自己語りから**他人との比較**へ軸足を移している。

**個人開発への含意**: 供給問題（誰がコンテンツを作るのか）が存在しない唯一の型。
軸5が最初から満点。**latent が属しているのはこの型である。**

## 4. 失敗パターン（作る前にチェックする）

1. **軸6がゼロのまま出す** — 初動は出るが3ヶ月で消える。BeReal 型の死に方。
2. **新規性が切れてから機能を足す** — 機能追加が軸2の制約を壊し、体験の芯が薄まる。
   通称 feature creep。BeReal・Clubhouse に共通する。
3. **「ありのまま」を機能名にする** — ありのままは制約の**結果**であって、目標に置くと演技になる。
   制約だけ置いて、コンセプトは語らないほうが強い。
4. **出力がアプリ内で完結する** — 軸3がゼロ。広告費なしでは1ミリも広がらない。
5. **N≥5 でしか価値が出ない** — 個人開発では絶対に立ち上がらない。設計をN=2に落とせないか必ず検討する。
6. **驚きが1回で使い切られる** — 1回見て終わりの出力。次章の latent の現状がこれに該当する。

---

## 5. latent への適用

### 現状の6軸診断

latent は現在、写真ライブラリのメタデータのみをローカルで読み、
「N枚に1枚がスクリーンショットだった」という1つの事実を提示するアプリである（`lib/library.ts`, `App.tsx`）。

| 軸 | 現状 | 評価 |
|---|---|---|
| 強制関数 | なし。ユーザーが思い出したときだけ開く | × |
| 制約 | 強い。数字1つとバー1本まで削ぎ落とされている | ◎ |
| 観測可能性 | なし。共有導線がゼロ。結果は `ScrollView` に表示されるだけ | × |
| 社会的単位 | 自分自身 | ○ |
| コールドスタート | 満点。N=1 で完全に成立し、権限さえ通れば即座に価値が出る | ◎ |
| 反復耐性 | ゼロ。2回目に開いても数字はほぼ同じ。驚きは初回で消費される | × |

**診断**: latent は Spotify Wrapped 型（軸5が最初から満点）でありながら、
Wrapped が持っている軸1（年1回・全員同時）と軸3（スクリーンショット型の出力）を持っていない。
一番おいしい部分だけが欠けている状態。

そして軸6がゼロなのは、Wrapped 型としては**設計ミスではなく未完成**である。
Wrapped は「1年待たせる」ことで軸6を解決している。latent は待たせる仕組みを持っていない。

### 打ち手（優先度順）

#### 打ち手A: 結果を1枚の共有画像にする（軸3を×→◎）

**最も費用対効果が高い。** 現在すでに「1つの強い数字」という Wrapped と同じ素材を持っているのに、
それを外に出す口がない。縦長1枚・数字が大きい・アプリ名が入る画像を生成し、共有シートに流すだけでよい。

- 変更範囲: `Result` コンポーネントに共有ボタンを追加し、ビューを画像化して共有する
- 効いてくる軸: 軸3（観測可能性）
- 注意: latent のコンセプトは「あなたの写真は見ません」なので、
  共有画像に写真そのものが1ピクセルも入らないことは、むしろ強い訴求になる

#### 打ち手B: 蓄積型に変えて軸1と軸6を作る

前回スキャン時の集計をローカルに保存し、**差分**を見せる。

- 「先週から、世界を撮ったのが12回、画面を撮ったのが83回」
- これができると、週1回の通知（軸1）が正当化される。通知に見せる中身ができるため
- 効いてくる軸: 軸1（強制関数）、軸6（反復耐性 / 蓄積型）
- 副作用: アプリが「1回で終わる驚き」から「毎週見るもの」に変わる。これが latent 最大の弱点の解消になる

#### 打ち手C: 社会的単位を2人にする（軸4・軸5）

友達と比率を比べる。ただし latent の「何もアップロードしない」という設計思想と
正面から衝突するため、比率という**1つの数値だけ**を送る形に限定する必要がある。
打ち手A・Bを済ませてから検討すべきで、先にやるべきではない。

### 推奨する順番

```
打ち手A（共有画像）→ 打ち手B（週次の差分）→ 効果を見てから打ち手C
```

A は既存の強みをそのまま外に出すだけで、コンセプトを一切壊さない。
B は latent の最大の欠陥（軸6=ゼロ）を直す本命。
C はコンセプトとの衝突があるため、A・B の結果を見てから判断する。

---

## 6. 新しいアイデアを検証する手順

アイデアを思いついたら、コードを書く前にこの順で潰す。

1. **1文で書く** — 「〇〇したら、△△が起きる」の形。書けないなら、まだメカニクスになっていない。
2. **軸5を先に判定する** — N=1 または N=2 で価値が出るか。No なら個人開発では捨てる。
3. **軸6を先に判定する** — 200日目に何が違うか。無限供給/低頻度イベント/蓄積 のどれで解くかを決める。
   どれでもないなら、初動だけのアプリになると確定する。
4. **軸3の出力形を先に描く** — 外に出るときの絵を1枚描く。描けないなら広告費が必要になる。
5. **軸2の制約を1つに絞る** — 制約は増やすほど弱くなる。「2秒」「2分」「年1回」のように、
   一言で言えるものが1つだけあるのが理想。

軸1（強制関数）は最後でよい。軸6が解けていれば、通知に見せる中身は自然に決まる。
