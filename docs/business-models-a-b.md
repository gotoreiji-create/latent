# A案とB案のビジネスモデル — コストの置き場所が正反対

[新規企画5案](./new-mechanics-from-scratch.md) の A「せーの」と B「かさね」について、
[マネタイズ設計](./monetization.md) の結論を当てはめて損益まで詰める。

計算の前提となる外部条件は次の2つ。どちらも実際の料金表に基づく。

| 前提 | 値 | 備考 |
|---|---|---|
| ストア手数料 | **15%** | Apple / Google 両方の小規模事業者プログラム。年間収益100万ドル未満が条件 |
| オブジェクトストレージ | **$0.015/GB・月、転送量無料** | Cloudflare R2。書き込み $4.50/100万、読み出し $0.36/100万。無料枠 10GB |

為替は1ドル150円で概算。**以下の売上予測は前提を置いた試算であり、実測値ではない。**

---

## 1. 結論から — 2案はコストの置き場所が正反対

| | A せーの | B かさね |
|---|---|---|
| 成長のしかた | **確定的** — 1人が必ず1人連れてくる | **確率的** — 出力が当たるかどうか |
| 集客コスト | 構造的にゼロ（招待が機能そのもの） | 自力で作る必要がある |
| 変動費 | あり（画像の保存） | ほぼゼロ（端末内で完結） |
| 収益の型 | **ストック**（積み上がる） | 買い切り＝**フロー** ＋ バックアップ＝ストック |
| 課金の必然性 | 高い（関係＋アーカイブ） | 低い（端末内なので「なぜ払う？」が発生） |
| 収益が立つまで | 早い（1日目から価値がある） | 遅い（アーカイブに価値が出るまで数ヶ月） |

> **A はコストがサーバーに乗る。それは成長した「後」に、成長した「ぶんだけ」発生する。**
> **B はコストが集客に乗る。それは成長する「前」に、成果の保証なく発生する。**
>
> 個人開発では、**後払いのコストのほうが圧倒的に安全**である。

## 2. 企画A「せーの」— ビジネスモデル

### 2.1 課金単位は「人」ではなく「ペア」にする

これが A で最も重要な設計判断。

**片方が払えば、2人とも解放される。**

理由は2つ。

1. **購買動機が強くなる。** 「自分のために払う」より「相手のために払う」ほうが強い。
   N=2 のアプリだけが使えるレバーで、単独アプリには存在しない
2. **転換の機会が2倍になる。** ペアのどちらか一方が「はい」と言えばよい。
   個人課金なら2人を別々に説得する必要がある

ペア単価は個人単価より高く置ける。ここでは **月800円／ペア** を前提にする。

### 2.2 何を売るか — アーカイブが商品になる

[マネタイズ設計](./monetization.md) で確認したとおり、蓄積型では
**アーカイブが毎日ぶんだけ価値を増す**ので、そこを商品にする。

| プラン | 内容 |
|---|---|
| **無料** | 毎日のお題・撮影・同時開示はすべて使える。**過去も全期間見られる**が、7日より前は低解像度 |
| **有料 月800円／ペア** | 全期間フル解像度・年次の書き出し・複数ペア・2人だけの自作お題 |

**重要なのは「無料でも過去が見られる」こと。**
アーカイブを消したり隠したりはしない。ユーザーは何も失わない。
見えてはいるが粗い、という状態が、そのまま自然な購入理由になる。

この設計は原価にも効く。無料ペアの保存量が10分の1になるので、
**無料ユーザーが増えても原価がほとんど増えない。**

### 2.3 絶対に売らないもの（再掲）

撮り直し・フィルタ・お題スキップ・時間制限の解除。
これらは軸2の制約そのものであり、売った瞬間に BeReal の失敗を有料で再現することになる。

### 2.4 原価の実数

前提：1ペア1日2枚。フル解像度 300KB、低解像度 30KB。**1万ペア（2万MAU）**、ペア転換率7%。

**保存量（1年後）**

| 内訳 | 計算 | 容量 |
|---|---|---|
| 有料700ペア（フル・全期間） | 700 × 219MB | 153GB |
| 無料9,300ペア（直近7日フル・常時） | 9,300 × 4.2MB | 39GB |
| 無料9,300ペア（8日目以降の低解像度） | 9,300 × 21.9MB | 204GB |
| **合計** | | **約396GB** |

396GB × $0.015 = **約$6/月**。2年後でも約750GB で **約$11/月**。

**オペレーション**

- 書き込み：2万人 × 1日1枚 = 月60万回 → 無料枠1,000万回の内側
- 読み出し：1枚あたり5回見られるとして月300万回 → 無料枠1,000万回の内側
- **転送量は R2 なので無料**（ここが S3 との決定的な差。画像アプリの原価は通常ほぼ転送量）

**サーバー・DB**：ペア紐付けと配信のみ。マネージドサービスで **$25〜50/月**。

> **原価合計 ≈ 月 $35〜60 ≈ 5,000〜9,000円。**

### 2.5 損益（目標到達時）

前提：1万ペア、ペア転換率7% = 有料700ペア。

| 項目 | 金額／月 |
|---|---|
| 総売上（700ペア × 800円） | 560,000円 |
| ストア手数料 15% | −84,000円 |
| 原価（R2＋サーバー） | −8,000円 |
| **粗利** | **約468,000円** |

年間約560万円。**粗利率およそ98%。**

保守的に転換率4%（有料400ペア）でも、粗利は月約264,000円・年約320万円。

### 2.6 「上位10%」への距離

[前作](./monetization.md)で確認した上位10%の閾値は月商2,574ドル ≈ 386,000円。
ペア単価800円なら **有料483ペア**で到達する。

- 転換率7%なら 6,900ペア（13,800 MAU）
- 転換率4%なら 12,000ペア（24,000 MAU）

### 2.7 リスク

1. **お題365個が書けるか。** 最大の関門であり、コードの問題ではない
2. **N=2 の脆さ。** ペアの片方が離脱すると2人とも死ぬ。
   有料機能の「複数ペア」は、ARPU 施策であると同時に**この脆さのヘッジでもある**
3. **画像を預かる責任。** 削除要求への対応、年齢確認、未成年利用への配慮。
   端末内で完結する latent とは責任の重さが違う
4. **無料の粗さがきつすぎると印象を損ねる。** 「見えるが粗い」の匙加減は慎重に

## 3. 企画B「かさね」— ビジネスモデル

### 3.1 まず、B には固有の問題がある

**端末内で完結するアプリは「なぜ払うのか」が成立しにくい。**

写真は自分の端末にあり、撮っているのも自分。
ここに月額を課そうとすると、ユーザーは素直にこう思う —
「自分の写真を自分の端末で見るのに、なぜ毎月払うのか」。

軸4が「自分自身」であることの弱さが、そのまま出る。

### 3.2 答え — 買い切り ＋ バックアップ月額

継続課金が正当化できるのは、**実際に継続的なコストと価値が発生しているもの**だけ。
B においてそれは1つしかない。**バックアップである。**

蓄積型アプリで300日続けたタイムラプスを端末の紛失で失うのは、実際に恐い。
これは本物の継続価値であり、こちらにも本物の継続コストがある。だから正当化できる。

| プラン | 価格 | 内容 |
|---|---|---|
| **無料** | — | 被写体1つ・書き出しにウォーターマーク |
| **買い切り** | 1,000円 | 被写体を無制限・フル画質書き出し・ウォーターマーク除去 |
| **バックアップ** | 月300円 | クラウド保存・機種変更時の復元 |

### 3.3 原価の実数

- **買い切りのみの利用者：原価ゼロ。** サーバーに一切触れない
- **バックアップ利用者のみ**：1日1枚 × 300KB = 110MB/年/人。
  1,000人でも1年後110GB → **約$1.7/月**

原価はほぼ無視できる。ここは B の明確な強み。

### 3.4 損益と、買い切りの落とし穴

上位10%の閾値（月商約386,000円）に届かせる経路は2つある。

| 経路 | 必要量 | 性質 |
|---|---|---|
| 買い切り1,000円のみ | **毎月386本を売り続ける** | **フロー**。売れた月しか売上が立たない |
| バックアップ月300円のみ | 課金者1,287人 | ストック。積み上がる |

> **買い切りはストックにならない。** 毎月ゼロから積み直す必要がある。
> A のサブスクは積み上がるが、B の買い切りは毎月リセットされる。

現実的には併用になる。仮に累計5万DL・買い切り率5%なら、
2,500本 × 1,000円 = 250万円（手数料後 約212万円）の一時収入。
これは大きいが**一度きり**で、翌年はまた新規DLを取りにいく必要がある。

バックアップの継続課金が育てば安定するが、
**ユーザーがアーカイブに価値を感じるまで数ヶ月かかる**ため、収益は後ろ倒しになる。

### 3.5 B の集客について、公平に書いておく

B の弱点を「集客コストが高い」と単純化するのは不正確である。

B の軸3（観測可能性）は5案中で最も強い。
ブレのないタイムラプスは、それ自体が非常に強い拡散素材になる。
**出力そのものが広告になる**ので、広告費が必須というわけではない。

正確な弱点は、コストの高さではなく **確実性のなさ** である。

- **A の成長は確定的** — 1人が必ず1人連れてくる。仕組みで保証されている
- **B の成長は確率的** — 動画が当たれば伸びるが、当たらなければ伸びない

## 4. 比較と推奨

### 損益の形（目標到達時・月次）

| | A せーの | B かさね |
|---|---|---|
| 売上の型 | ストック（積み上がる） | 買い切り＝フロー ＋ バックアップ＝ストック |
| 想定粗利 | 月 約468,000円（転換率7%時） | 買い切り一時収入 ＋ バックアップ次第 |
| 原価 | 月 約8,000円（売上の約2%） | ほぼゼロ |
| 集客 | 仕組みで保証 | 出力次第（強いが不確実） |
| 収益化までの時間 | 短い | 長い |

### 推奨：A「せーの」

前回は「Aを推奨、ただしバックエンドを持ちたくないならB」と書いた。
**原価を実数で出したことで、この但し書きは弱くなった。**

A のバックエンド費用は、2万MAU 規模で **月8,000円程度**、売上の約2%にすぎない。
R2 のように転送量が無料のストレージを選べば、画像アプリ最大の原価が消えるためである。

つまり「B はサーバーが要らない」という優位は、**月8,000円の差でしかない。**
その8,000円と引き換えに A が得るのは、**確定的な成長と、積み上がるストック収益**である。
これは割に合う。

### B に残る役割

B が有効なのは次の場合に限られる。

- 継続的な運用責任（他人の画像を預かること）を負いたくない
- まず1〜2週間で何か出して、軸3（外に出る出力）を作る練習をしたい

その場合も、**B の収益設計は「買い切り＋バックアップ」**にすること。
買い切り単体はフロー収益であり、走り続けないと止まる。

## 5. 着手する場合の順番（A）

前作の検証手順は変えない。ビジネス面で追加すべきことは1つだけ。

1. お題を30個書く
2. **アプリなしで7日間、自分と友達1人で試す**
3. 出力の絵を1枚描く
4. 実装（ペア紐付け＋画像交換の最小構成）
5. **← 追加：ストレージは最初から転送量無料のものを選ぶ**

手順5は後から変えると移行コストが高い。
画像アプリの原価はほぼ転送量なので、**ここだけは最初に決めておく。**
